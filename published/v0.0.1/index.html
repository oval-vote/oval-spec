Oval Specification

Version 0.0.1, released November 7, 2026

Introduction

This is the specification for Oval, a plain-text file format for voting guides. It defines the Oval language, its characters, tokens, grammar, and the meaning of each construct.

For prospective implementers of the specification, it also describes how a conforming lexer, parser, validator, formatter, and compiler behave.

1Overview

A voting guide tells its readers what is on their ballot and how its author recommends they vote on each question, with optional reasoning behind each recommendation. Newspapers, advocacy groups, political clubs, religious organizations, and even individuals often publish guides before every election, almost always as prose: a web page, a PDF, a thread of posts. Written that way, the structure of a guide exists only in the author’s head and the reader’s eye. Publishing the same guide in more than one place means reformatting it by hand each time. Ballots are harder to model than they look, because election rules and their regional variations are numerous and inconsistent. Modeling recommendations is harder still: a recommendation can be nuanced, can rank candidates, can endorse some and warn against others, or can decline to take a position.

An Oval document represents a single voting guide. It states the election, the ballot or ballots, the contests and measures on each one, the candidates and parties, and the author’s position on each question. Structure is expressed with keywords and indentation. Reasoning is written as Markdown under the question it concerns.

oval 1

guide "Ashford Voter Guide"
election "November 3, 2026 General Election"
date 2026-11-03

ballot @city "City of Ashford"

  contest @mayor "Mayor" single
    campaign incumbent @bsantos "Beatriz Santos"
      designation "Mayor of Ashford"
    campaign @cfox "Carl Fox"
      designation "Small Business Owner"
    recommend
      support @bsantos
      justification:
        Santos has kept her 2022 promises on housing and transit. Fox has no plan beyond
        cutting a budget he has not read.

  measure @prop-a "Proposition A"
    subtitle "Library parcel tax renewal"
    recommend yes
      justification:
        Renews an existing tax at the same rate. Every branch stays open seven days a week.

Oval is designed around four design goals, in no particular order:

  • Readable by hand. An author with no programming background should be able to write a complete guide in a text editor and read it back as plain text. There is nothing to learn beyond a few keywords and indentation, and nothing to install to write a guide.
  • Explanations are first class. A good voting guide is not just a list of selections. It should also contain generally useful explanatory information about the election and the author’s reasoning behind their recommendations. Oval documents don’t just model ballots, they model this prose as well.
  • Checkable. A static validator should be able to catch an unfinished or self-contradictory guide before it is published, for example: a contest with no recommendation, a reference to a candidate who is not in that contest, or ranking recommended in a vote-for-one contest. A voting guide is either completely valid or completely invalid.
  • Exportable. A guide is readable as plain text, but most readers will want it in a richer format, such as a web page, a PDF, or a printed card. Tools that produce those kinds of outputs will want stricter input than Oval’s text format — one with a fixed shape, independent of Oval’s syntax, with every reference resolved and every count computed, so that rendering requires no lookup. A valid guide compiles to one JSON value with a fixed schema, and two guides that mean the same thing compile to the same value, so a renderer reads that output and never parses Oval itself.

Oval does not describe how a guide is presented, but it does describe how a guide can be presented using its canonical output. Rendering a guide as a web page, a printed card, a PDF file, or a comparison table is the job of tools built around the compiled output, and a document carries no layout, styling, or presentation instructions of its own. Oval also does not model the election beyond what the guide’s author chooses to say about it: there are no results, polling places, districts, or registration rules, and no attempt to be a source of record for who is running.

Specification

This document defines Oval in four parts, each building on the one before it:

  • The language. The lexical and syntactic grammar, which decides which sequences of characters are allowed in an Oval document, and the meaning of each construct. A document that follows the grammar is well-formed. A conformant parser accepts every well-formed document and reports where the grammar was broken in every other one.
  • Validation. The rules that ensure a voting guide is complete, correct, and consistent. Each rule says what it checks and whether breaking it is an error or a warning. A well-formed document that breaks no rule whose severity is error is valid. A conformant validator reports every error and every warning.
  • Formatting. The canonical style for Oval documents. A conformant formatter accepts every well-formed document and produces an equivalent document in that style. Formatting never changes the meaning of a document and never introduces an error or a warning.
  • Canonical output. The JSON value a valid document compiles to. It is the guide with every reference resolved and with the fields any renderer would otherwise recompute, in a shape fixed by a published JSON Schema. Compiled output should be unaffected by file organization, comments, whitespace, and formatting — two guides with the same meaning should compile to the same output.

The appendices collect the complete grammar and the list of keywords.

This document does not define the interface of any tool. The names of commands, the wording and layout of diagnostics, and how an editor presents them belong to the tools. It does not render Markdown; notes and justifications pass through to the output unchanged, limited to the Markdown profile of Section 2.2 so that every renderer shows them the same way. And it does not say how guides are published, distributed, or kept current once written.

Every Oval document begins with a version marker naming the major version of the language it was written in, so a tool knows how to read it before reading anything else. Within a major version, each edition of this specification only adds to the language; nothing is removed or changed. A tool built to a later edition therefore reads every document written to an earlier edition of the same major version, and a document that uses a construct its tool does not yet know fails at that construct rather than being misread.

1.1Notation

Grammar productions are written in the following notation. A syntactic production, written Name : Rule, matches tokens; a lexical production, written Name :: Rule, matches characters. Alternatives are listed one per line. X? is optional, X* is zero or more, and X+ is one or more. Literal text is in backticks; in a syntactic production it matches a Word or Punctuator token with exactly that text. Prose that stands in for a rule is in double quotes. one of introduces alternatives that are each a single token, and but not excludes alternatives. Production names are UpperCamelCase, and on the website every name links to its definition.

The complete grammar is collected in Appendix A.

2Language

2.1Source Text

An Oval document is a sequence of Unicode code points encoded as UTF-8. Input that is not well-formed UTF-8, or that contains U+0000, is rejected as a whole and produces no tokens. A byte order mark (U+FEFF) at the start of the input is ignored; a formatter does not emit one.

SourceCharacter
any Unicode code point except U+0000

A document is divided into lines by line terminators.

LineTerminator
New Line (U+000A)
Carriage Return (U+000D)New Line (U+000A)
Carriage Return (U+000D)

All three forms are equivalent.

Oval is layout-sensitive: the structure of a document is given by the indentation of its lines, not by brackets or closing keywords.

A Word is a bare run of letters, digits, hyphens, and underscores that begins with a letter. The lexer accepts every such run; which words may appear where is decided by the syntactic grammar. 2.2.7MarkdownBlock

A MarkdownBlock is the body of a Markdown field: the lines following a line that ends in :.

MarkdownBlock
BodyLinelist
BodyLine
a line indented more than the opening line, or a blank line between two such lines

The opening line is any line whose last token, ignoring whitespace and comments, is :. After its Newline, the lexer looks ahead past any lines that are empty or contain only spaces to the next line with other content; a # is content here, since inside a body it is text. If that line is indented strictly more than the opening line, the body begins there and extends over every following line that is either blank or indented strictly more than the opening line, ending after the terminator of the last such line with content. If the next content line is not indented more, there is no body and no token.

The token covers the body’s raw text, from the first content line’s leading spaces through the last content line’s terminator (or end of input). Blank lines before and after the body are not part of it; they lex as BlankLine. Blank lines inside the body are part of it. Body lines do not participate in layout (Section 2.4): they produce no Newline, Indent, or Dedent, and the indentation stack is unchanged after the body.

The body is opaque. Inside it # is not a comment, @, ", and tabs are ordinary characters, and no other token is recognized. The body is Markdown; the Markdown profile below says which constructs it may use, and validation (markdown-profile) enforces it. The lexer does not inspect the body.

The token’s value is derived from its text: the common leading indentation of its non-blank lines is removed from every line, lines containing only spaces become empty, every line terminator becomes U+000A, and the final terminator is dropped. Parsers expose the value; the token itself keeps the raw text.

A : followed on its line by anything other than whitespace, a comment, or a line terminator does not open a body; whether that is valid, and whether the word before the : is one that takes a Markdown body, is the parser’s concern. A Markdown field whose opening line has no body is a syntax error (missing-body), not a lexical one; omit the field instead.

2.2.8Markdown Profile

The value of a MarkdownBlock is Markdown as defined by CommonMark 0.31.2, extended with tables as defined by the GitHub Flavored Markdown tables extension. Oval permits a subset of that language, the Markdown profile, so that every renderer shows a body the same way. A body that uses a construct outside the profile is invalid (markdown-profile). The profile is not part of the token: the lexer and parser never inspect a body, validation checks it, and the body reaches the canonical output unchanged.

A body may contain these block constructs:

  • Paragraphs.
  • ATX and setext headings. A heading in a body is subordinate to the construct the field belongs to; a renderer places it under its own heading for that construct and may change its level.
  • Block quotes.
  • Bullet lists and ordered lists, nested to any depth.
  • Tables.
  • Hard line breaks, written as two trailing spaces or a backslash before the line terminator.

And these inline constructs:

  • Emphasis and strong emphasis.
  • Links: inline links, reference links with their link reference definitions in the same body, and autolinks. Every link destination is an absolute http or https URL, and http draws a warning (insecure-url).
  • Backslash escapes, and entity and numeric character references.

A body may not contain:

  • Code, in any form: indented code blocks, fenced code blocks, and code spans.
  • Raw HTML, as blocks or inline.
  • Images.
  • Thematic breaks.

Everything CommonMark does not recognize is rendered as plain text. Strikethrough, task list items, footnotes, and bare URLs are extensions outside the profile. A body containing them is valid but shows them as the characters written; write a URL as a link.

Four or more spaces of indentation beyond the body’s common minimum begin an indented code block in CommonMark. A paragraph or list item indented that far is therefore a markdown-profile error; reduce the indentation. A formatter preserves relative indentation inside a body, so it never introduces or removes one.

A # begins a comment that runs to the end of the line, except inside a MarkdownBlock body or a String, where it is an ordinary character. A comment may follow tokens on the same line.

A line containing nothing but whitespace and a comment is a blank line. Its terminator lexes as BlankLine rather than Newline, so blank lines are ignored by the parser wherever they appear. Inside a MarkdownBlock body blank lines are part of the body and separate paragraphs.

Horizontal tab (U+0009) is not whitespace. A tab anywhere outside a String, a Comment, or a MarkdownBlock body is a lexical error (illegal-tab). This rule exists so that indentation (Section 2.4) is unambiguous.

2.4Layout Tokens

Oval’s block structure is expressed by indentation. The lexer converts indentation into three synthetic tokens, following the approach of Python.

LayoutToken
Newline
Indent
Dedent
Newline
the end of a line that contains tokens
Indent
an increase in indentation, at the start of a line
Dedent
a return to an enclosing indentation, at the start of a line or at the end of input

All three are zero-length except Newline at a line terminator. Indent and Dedent are positioned at the first token of the line that triggers them, after that line’s leading Whitespace. Because they have no text, the lossless property of Section 2.2 is preserved.

A line’s indentation is the number of U+0020 characters before its first other character. A tab is an “other character” (and an error). The lexer maintains a stack of indentation levels, initially [0].

  • At the end of each line with tokens, emit Newline covering the line terminator. A blank line emits BlankLine instead and does not affect the stack.
  • Before the first token of a line with tokens, compare its indentation n to the top of the stack:
    • If n is greater, push n and emit Indent.
    • If n is less, pop the stack and emit one Dedent per level popped until the top is less than or equal to n. If the top is then not equal to n, report an inconsistent dedent (inconsistent-dedent) over the line’s leading spaces and treat the line as being at the top’s level.
    • If n is equal, emit nothing.
  • At end of input, if the last line has tokens and no terminator, emit a zero-length Newline. Then emit Dedent for every level above 0.

So a block always closes with the sequence Newline Dedent, whether it is followed by another line or by end of input, and the grammar’s productions can end in Newline without an end-of-input special case.

The amount of indentation is not fixed; any increase opens a block. A formatter emits two spaces per level. A line indented more than its predecessor where the grammar does not permit a block is a syntax error (unexpected-block).

Lines inside a MarkdownBlock body do not participate in this process. The entire markdown block is considered one token.

A document is a Guide (Section 2.8) written at indentation zero. It opens with the version marker, then the document’s fields, then any top-level Party and Candidate declarations, then the root Ballots. These four groups appear in that order; within the fields and within the declarations, order is free. The grammar leaves the ballots optional for the same reason it leaves guide optional: a document with none is invalid (empty-document), not malformed.

There is no closing token. The document ends at end of input.

Version marker. oval 1 names the major version of the language the document is written in. It is the first entry of every document; only blank lines and comments may precede it. The grammar leaves it optional for the same reason it leaves guide optional (missing-guide-field): a parser can then build a tree for a document that lacks it and say exactly what is missing. A document without a marker, or whose marker names a major version the implementation does not support, is invalid (unsupported-version). The Integer is written without leading zeros; a formatter removes them.

This specification defines major version 1. Within a major version, each edition of this specification only adds to the language, so an implementation of a later edition accepts every document written to an earlier one. A construct that an implementation does not know is a lexical or syntax error at that construct, which is how an older implementation reports a document that needs a newer edition. A new major version is reserved for a change that removes a construct or alters the meaning of one.

2.7Declarations and References

Entities (Party, Candidate, Ballot, Contest, Measure) are declared exactly once each and may be referred to any number of times.

Identifier
@Word
Reference
Identifier

An identifier names an entity. It is the punctuator @ followed by a Word, written without whitespace between them; a formatter removes any. Identifiers are case-sensitive, and two identifiers are the same if their words are identical. Because every identifier begins with @, no word is reserved: @ballot is an ordinary identifier.

A declaration is an Identifier followed immediately by a String, after the entity’s keyword; the string is the entity’s name or title. A reference is a bare Identifier. This is the single rule for every entity kind:

candidate @jlee "Jordan Lee"     — declares @jlee
campaign @jlee                   — refers to @jlee
campaign @kobi "Kwame Obi"       — declares @kobi here, inline
party @dem "Democratic"          — declares @dem
party @dem                       — refers to @dem

Some entities may be declared inline at their first use instead of at the top of the document. Where a reference is permitted, the grammar says whether a declaration is also permitted in that position. An inline declaration is the same declaration as a top-level one; it is simply written elsewhere. Validation requires every reference to name a declaration (undeclared-reference) and every identifier to be declared at most once (duplicate-declaration), wherever that is.

Identifiers share one namespace across all entity kinds (duplicate-declaration).

3Validation

Validating a document is three stages run in order, each on the output of the one before:

  1. Lexing turns the source text into the tokens. Text that cannot be tokenized becomes an Error token and a lexical error. Lexing covers every byte of the input, so the token stream is complete even when it contains errors. An exhaustive list of lexical errors is described below.
  2. Parsing matches the token stream against the syntactic grammar and builds a tree. A token the grammar does not expect is a syntax error. A document that lexes and parses without error is well-formed. An exhaustive list of syntax errors is described below.
  3. Validation checks the tree against the list of validation rules. A well-formed document that produces no error is valid. Warnings do not affect validity, but a compliant validator should still report them.

Every error at every stage has an identifier and a range in the source. Identifiers are stable across editions; tools should report errors by identifier. A validator reports every lexical error, every syntax error, and every rule the document breaks, in source order, so that an author can see them all in once pass.

3.1Lexical Errors

Where the text cannot be tokenized at all it becomes an Error token spanned exactly by one error; where a token is recognizable but flawed, the token keeps its kind and the error points at the flaw within it.

After an error the lexer continues, using the recovery given for each error below, so that every error in a document is reported in one pass and so that the token stream still covers every byte. The recoveries are normative: two implementations given the same broken document produce the same tokens and the same errors.

A tool that only needs to accept or reject a document may stop at the first error instead. It then reports a subset of the errors this section specifies and is not lexer- or parser-conformant (Section 4), since those levels exist for tools that must make sense of every byte of a broken file; the documents it accepts are exactly the documents a conformant implementation accepts.

Note Each error below is followed by an example that lexes without error and a counter-example that produces the error, each with its token sequence: every token in order, with its kind and its text. A space is shown as ␣, a tab as ⇥, and a line terminator as ↵. Zero-length tokens have no text.

3.2Syntax Errors

The parser reads the token stream one entry at a time. An entry is a line together with the block, if any, indented beneath it. The grammar says which entries each block accepts and which tokens each line may carry, and the parser reports a syntax error at the first token it cannot accept. A document with a syntax error is not well-formed.

Every syntax error has a recovery, so that two implementations build the same tree and report the same errors for the same broken document, and so that an editor can keep working on a half-written file. A tool that only needs to accept or reject a document may stop at the first error on the terms Section 3.1 gives. There are four recoveries, named here and referred to by each error below:

  • Skip the line. The tokens from the unexpected one to the end of the line are discarded. The construct keeps whatever was parsed before them, and parsing continues on the next line.
  • Skip the entry. The entire entry is discarded, including its block. Parsing continues with the next entry at the same level.
  • Assume the missing token. Nothing is discarded. Parsing continues as if the token were present; the construct is kept with nothing in that position, and validation treats it as absent.
  • Set the entry aside. The entry is parsed in full, so that errors inside it are still reported, but it contributes nothing to the construct that contains it.

Discarded and set-aside text remains in the tree inside an error node, so the tree still covers every byte of the source and a formatter can refuse the document rather than guess at it.

The errors below are exhaustive, by position. A token the grammar cannot accept at the start of an entry is an unexpected entry, or an unexpected block if it is an Indent; one in the middle of a line is an unexpected token; and a line or entry that ends where the grammar requires more is one of the missing-token errors. The remaining errors are entries that fit the grammar but not the document’s structure. A parser never needs a fallback error.

The parser skips Error tokens from the lexer as it skips comments and whitespace, so a lexical error is the only diagnostic for the text it covers. On a line that contains an Error token, no missing-token error is reported, since what is missing may be the text the lexer rejected. A line whose only token the parser does not skip is its terminator is treated as blank.

Occurs when a line carries a token the grammar does not accept at that point and the line has not ended: a value of the wrong kind, a token after a complete entry, a second value where only one is allowed, or text on the same line after a Markdown field’s :. The error is reported as unexpected-token and spans from that token to the end of the line. To recover, skip the line. The diagnostic names what was expected.

3.4Warnings

A warning marks a document that is valid but probably not what its author intends: something is unused, duplicated, or unbalanced in a way the grammar and the errors above allow. A tool may let an author silence a warning; this specification does not say how.

4Conformance

Three conformance levels are defined so that tools can claim what they implement.

  • Lexer-conformant. Tokenizes any input per Sections 2.2–2.4, producing tokens that cover every byte, and reports lexical errors with the ranges and recovery of Section 3.1. Sufficient for syntax highlighting.
  • Parser-conformant. Accepts exactly the well-formed documents of Section 2 and produces a tree that covers every byte of the source, with the recoveries of Section 3.2. Sufficient for a formatter.
  • Validator-conformant. Parser-conformant, and reports every Section 3 rule with its identifier and severity.
  • Compiler-conformant. Validator-conformant, and for every valid document produces the canonical output of Section 5, byte-for-byte equal to the reference implementation’s after JSON normalization (key order and whitespace disregarded).

A conformance claim names the major version of the language and the edition of this specification it implements. An implementation reports documents of another major version under unsupported-version rather than attempting to process them.

A conformance test suite (not yet written) will consist of well-formed and malformed documents, and for each well-formed document the expected validation report and canonical resolved output.

5Canonical Output

Compiling a valid document produces one JSON value: the data model with every reference resolved, plus derived fields that any renderer would otherwise recompute. Its shape is fixed by schema/guide.schema.json, a JSON Schema (draft 2020-12), which is normative. This section explains the conventions the schema follows, lays out the shape it fixes, and defines the derived fields. The output is called canonical because two conformant implementations must produce the same value for the same document; it is a contract between implementations and consumers, not a document for people to read.

The output is the semantic model, not the syntax tree. It carries no source positions, comments, or whitespace, so two parsers cannot disagree about it on formatting. Tools that need positions use the syntax tree or the diagnostics.

5.1Conventions

  • Keys mirror the language. Every field that comes from a keyword uses that keyword’s exact spelling: if_yes, fiscal_impact, no_position. Derived fields use the same snake_case style. The one exception is the contest’s voting method, which the language writes on the header line without a keyword; it is the method object, because kind is the discriminator used by every item object.
  • Arrays, not maps. Order is meaning in Oval, so parties, candidates, ballots, items, campaigns, members, and tiers are arrays in document or ballot order. Entities carry an id, and references are identifier strings without the leading @.
  • Absent fields are omitted. An optional field the author did not write is not present; it is never null. supporters and opponents therefore have three states: omitted (not researched), [] (researched, none), or a list.
  • Booleans are always present. incumbent, withdrawn, and no_position are written even when false.
  • The root echoes the version marker. oval is the document’s declared major version as an integer, 1. Later editions of the same major version only add keys to the output, so a consumer written to an earlier edition reads the output of a later one.
  • Discriminated unions use kind. Every item in a ballot or section has a kind of section, contest, measure, or ballot, and root ballots carry kind: "ballot" too, so one type describes a ballot anywhere. method.kind and stance.position discriminate the same way.
  • Markdown is a string with common indentation removed, terminators normalized to \n, and no trailing terminator (the value of Section 2.2). It is within the Markdown profile. Rendering it is the consumer’s job.
  • Campaigns are referred to by index within their contest’s campaigns array, since they have no identifiers.
  • Strict producers, tolerant consumers. The schema forbids unknown keys so that a producer’s mistakes are caught. Consumers should ignore keys they do not recognize, because a later edition of this specification may add fields. Removing or renaming a field takes a new major version.

6Formatting

A formatter rewrites a well-formed document into the canonical style below. Formatting never changes meaning: the formatted document has the same significant tokens, the same Markdown values, and compiles to the same canonical output (Section 5) as the original. Formatting is idempotent.

A formatter refuses a document with lexical or syntax errors and reports them instead. Recovery from errors produces a tree whose shape the author did not intend, and reformatting around it could move text in surprising ways.

6.1Whitespace

  • Line terminators become U+000A. The document ends with exactly one.
  • Trailing spaces are removed from every line, except content lines inside a MarkdownBlock, where two trailing spaces are a hard line break in Markdown and are preserved. Whitespace-only lines inside a body become empty.
  • Every line is indented two spaces per enclosing block, whatever the source used. A MarkdownBlock body is indented one level deeper than its keyword line; each body line keeps its indentation beyond the body’s common minimum, so lists and continuation lines keep their shape.
  • Tokens on a line are separated by one space. : and , attach to the token before them, and @ to the word after it. A trailing comment is preceded by one space.

6.2Blank lines and comments

  • Runs of blank lines collapse to one. Blank lines inside a MarkdownBlock body are content and are kept exactly.
  • A blank line and any comment lines after it belong to the next line with tokens: they are indented to that line’s depth and move with it when entries are reordered (Section 6.3). A blank line the author wrote at the start of a block stays; one that would begin a block only because its entry was reordered is removed. Blank lines at the start and end of the document are removed. A formatter never inserts a blank line. Comments after the last line of the document are placed at column zero.

This attachment rule is a formatting decision, not a parsing one. The parser attaches a comment to whichever node is open when the next significant token is consumed, which puts a comment just before an indented block in the parent and a comment just before a dedent in the inner block. Neither is where a reader would say the comment belongs, so the formatter corrects both.

6.3Entry order

Within a block, entries are grouped by kind in the order Appendix A lists the block’s alternatives, and kept in source order within a group:

Block Order
Document version marker; fields; then declarations; then ballots
Ballot fields; then sections, contests, measures, and sub-ballots
Section fields; then contests and measures
Contest fields; campaigns; recommendations
Campaign members; then fields
Recommendation support tiers; oppose; then justification and note
Measure fields; recommendations
Party, Candidate, Member, inline Party fields only

Fields keep their source order relative to one another. Children that carry meaning in their order (campaigns, members, tiers, items) are never reordered relative to one another.

Whether a formatter should instead place fields first in every block, or impose an order among fields, is undecided and is expected to become a configurable option rather than a rule here.
